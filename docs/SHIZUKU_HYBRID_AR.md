# AL-thmany 2.7.0 — Shizuku Adaptive Fast Runtime

يبدأ الإصدار 2.7.0 بمحاولة المسار الدائم Event-first بدل تعطيله افتراضيًا. إذا سمح Android/Knox بالجلسة الدائمة تُستخدم أحداث واجهة واتساب وشجرتها مباشرة، وإذا رفضها النظام ينتقل المحرك تلقائيًا إلى `uiautomator dump` المتوافق دون فقد الرابط الحالي.

- بعد ضغط Join في المسار المتوافق، يجري المحرك أربع محاولات قصيرة لإثبات نشاط محادثة واتساب عبر **الحزمة الدقيقة + Android user الدقيق + نشاط Conversation معروف**. عند ثبوتها يفتح الرابط التالي فورًا من دون Back ومن دون dump إضافي.
- سرعة الانتقال موحدة مع Accessibility: من 0 إلى 10 ثوانٍ بدقة 100ms، والقيمة 0 تعني تسليمًا مباشرًا بعد إثبات النتيجة.
- حد الجولة الصريحة أصبح 1000 رابط، مع بقاء القائمة المحلية حتى مليون رابط فريد.
- الشاشات الملتبسة تبقى خاضعة للتحقق الدلالي، وRestriction/Retry Later يوقفان التشغيل؛ لا يوجد تجاوز لقيود واتساب أو Knox/DPC.

قبل تشغيل قائمة كبيرة، اختبر رابطًا واحدًا داخل كل بيئة: الشخصي، ملف العمل، والمجلد الآمن، لأن رؤية shell لشجرة واتساب تختلف حسب الجهاز وسياسة الإدارة.

# AL-thmany 2.3.0 — Shizuku Smart Hybrid Runtime

في 2.3.0 أصبح Shizuku backend أكثر تحفظًا ودقة: لا يبدأ قبل فحص Binder/Permission/UserService ووجود AL-thmany وواتساب في نفس Android user وقراءة حجم الشاشة. كل Tap يحتاج عقدة UIAutomator من حزمة واتساب المحددة، درجة دلالية غير غامضة، وظهور نفس المرشح في لقطتين متتاليتين.

إذا اختفت UI hierarchy أو انقطع Shizuku أو أصبح الإجراء غامضًا، يتوقف التشغيل ويحفظ الرابط الحالي بدل تسجيل نتيجة تخمينية. نجاح Join لا يعتمد على اختفاء نافذة الدعوة فقط؛ يجب ظهور سطح واتساب قوي ومستقر مثل المحادثة أو الصفحة الرئيسية أو صفحة المجتمع.

**Community Traversal عبر Shizuku** أصبح متاحًا بشكل محدود ومشروط: فقط إذا كشف `uiautomator dump` صفحة المجتمع وصفوف القروبات بشكل دلالي. يستخدم صفوفًا آمنة فقط، إجماع لقطتين، dedupe، وحدود 256 صفًا/40 scroll/3 Back مع no-progress guard. إذا Knox لا يكشف هذه العناصر فلا يحاول المحرك تجاوز ذلك.

> مهم: Shizuku ليس تجاوزًا لـ Knox أو DPC. الاختبار الفعلي على جهازك هو الذي يحدد إن كانت واجهة Secure Folder/Work مرئية لـ UIAutomator.

# AL-thmany 2.2.0 — Shizuku Hybrid Engine

هذا المسار يضيف Shizuku كمحرك تشغيل ثانٍ **اختياري وتجريبي** بجانب محرك Android Accessibility الموجود. الهدف هو اختبار ما إذا كانت صلاحية ADB shell التي يوفرها Shizuku تستطيع رؤية واجهة WhatsApp والتحكم بها في بيئة الجهاز الحالية عندما لا تكون Accessibility متاحة.

## ما الذي يفعله المحرك؟

- يطلب إذن Shizuku من المستخدم ولا يعمل بدونه.
- يشغل UserService بهوية Shizuku (عادة shell عند التشغيل عبر ADB/Wireless debugging).
- يتحقق من أن AL-thmany وWhatsApp المحدد موجودان في Android user/profile نفسه قبل فتح أي دعوة.
- يفتح رابط الدعوة صراحة في حزمة WhatsApp المقفلة للجلسة.
- قبل أي Tap يتأكد مرة أخرى أن حزمة WhatsApp المحددة هي النافذة الأمامية.
- يحصل على UI hierarchy بواسطة `uiautomator dump` ثم يمرر النصوص/المعرفات إلى مصنف AL-thmany الدلالي الحالي.
- لا ينقر إحداثيات عمياء: Tap لا ينفذ إلا على bounds مرتبطة بعقدة دلالية آمنة مثل Preview / Join / Request / Confirmation.
- Restriction / Retry later يبقى Hard Stop ولا تتم محاولة تجاوزه.
- إذا كانت Knox/Work Profile تمنع UI dump أو input، يتوقف المحرك برسالة TARGET_UNSUPPORTED ويحافظ على بقية القائمة بدل الاستمرار بنقرات مجهولة.

## اختيار المحرك

في الإعدادات يوجد الآن:

- **Auto**: يفضل Accessibility عندما تكون مفعلة، وإلا يستخدم Shizuku إذا كان جاهزًا.
- **Accessibility**: يجبر استخدام المحرك الأصلي.
- **Shizuku**: يجبر استخدام محرك Shizuku ويمنع البدء إذا لم يكن Shizuku جاهزًا.

وجود Accessibility مفعلة على الهاتف لا يسبب تشغيل المحركين معًا؛ عندما تكون جلسة Shizuku نشطة تتجاهل خدمة Accessibility أحداث الأتمتة حتى لا يحدث Double Click.

## إعداد Shizuku بدون Root (Android 11+)

1. ثبّت تطبيق Shizuku من مصدره الرسمي.
2. فعّل Developer options ثم Wireless debugging.
3. من Shizuku اختر Pairing واقرن الجهاز ثم Start.
4. افتح AL-thmany → الإعدادات → محرك التشغيل → Shizuku أو Auto.
5. اضغط **منح إذن Shizuku** ووافق من نافذة Shizuku.
6. اضغط **اختبار Shizuku**.
7. يجب أن تكون النتيجة شبيهة بـ: `binder=ON; permission=GRANTED; shell=OK; ui=UI_DUMP_OK`.
8. اختر نسخة WhatsApp المستهدفة ثم ابدأ أول اختبار **برابط واحد فقط**.

في التشغيل بدون Root قد يحتاج Shizuku إلى إعادة التشغيل بعد إعادة تشغيل الهاتف.

## Secure Folder / Work Profile

Shizuku ليس تجاوزًا لـKnox أو DPC. نجاح Binder وPermission لا يعني تلقائيًا أن shell يستطيع رؤية UI داخل Secure Folder. لذلك النسخة 2.2.0 تعمل بأسلوب Probe-first: إذا لم يستطع `uiautomator dump` قراءة hierarchy في تلك البيئة، يتوقف بأمان ولا يحقن Tap عشوائيًا.

للأمان، يجب اختبار رابط واحد أولًا. إذا أثبت الاختبار أن UI hierarchy مرئية وأن input يصل إلى WhatsApp الصحيح، يمكن توسيع Shizuku backend لاحقًا لمعالجة Community subgroup traversal في نفس الجهاز. حتى 2.2.0، **التجول التلقائي داخل قروبات المجتمع الفرعية يبقى متاحًا بالكامل في Accessibility backend فقط**؛ Shizuku backend يعالج رابط المجتمع الخارجي Join/Request ولكنه لا يجازف بالنقر على صفوف فرعية قبل إثباتها على الجهاز.

## حدود التشغيل

- حد التشغيل الصريح: 1000 رابطًا لكل تشغيل.
- سعة القائمة المحلية: حتى 1,000,000 رابط فريد.
- Scheduled start عبر Shizuku غير مفعل في 2.2.0؛ الجدولة تبقى في Accessibility backend.
- لا توجد محاولة لتجاوز WhatsApp Restriction/Retry later أو Knox/DPC.
# إصلاح الضغط والتسلسل في 2.7.4

عندما يثبت `dumpsys activity` أن واتساب المحدد داخل Android user الصحيح هو الواجهة الأمامية، لكن Persistent UiAutomation و`uiautomator dump` يعرضان Launcher، يستطيع 2.7.4 أخذ Screenshot محلية عبر Shizuku والبحث عن زر واتساب الإيجابي الأخضر العريض في الجزء السفلي. الزر العائم الصغير وأي مستطيل غير أخضر أو ضيق يُرفضان.

بعد لمسة مباشرة داخل حدود الزر المكتشف، يتحقق المحرك من اختفائه. إذا بقي يعيد اللمسة مرة واحدة فقط، ثم يغلق السطح بدل الوقوف. إذا اختفى يميز محادثة Join عبر exact-user activity proof؛ وإلا يسجل مسار Request، ينفذ Back المكافئ لإغلاق X، ثم يفتح الرابط التالي وفق الفاصل المحدد.

في Accessibility أصبح الضغط المباشر Gesture-first، لأن بعض إصدارات WhatsApp تعيد `true` لـ`ACTION_CLICK` من دون تنفيذ اللمسة. المحاولة البديلة لم تعد تُحجب بمفتاح idempotency للمحاولة السابقة.

# إصلاح التوافق في 2.7.3

على بعض أجهزة Samsung يظهر واتساب العمل على الشاشة بينما تبقى جلسة UiAutomation الدائمة مرتبطة بـLauncher في الملف الأساسي (`nodes=0; pkg=launcher`). يبدأ 2.7.3 فحص `uiautomator dump` متوافقًا بعد 180ms وبحد أقصى محاولتين. لا يضغط المحرك اعتمادًا على التوقيت أو المكان فقط؛ يجب أن يحتوي الفحص على عقدة دلالية من حزمة واتساب المحددة، ثم تبقى حدود الشاشة وفحص foreground مطلوبة.

إذا كان CloudDPC أو Knox هو Profile Owner فلن يستطيع AL-thmany تعديل سياسة allowlist. عند جاهزية Shizuku يجعل زر Work Controller المحرك المختار Shizuku بدل الادعاء بتغيير ملكية ملف العمل.
